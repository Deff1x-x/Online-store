# ЕДИНОЕ ТЗ «Клуб Оптовых Цен»: бэкенд + фронтенд
*Версия 1.0 · июль 2026 · рабочий документ для разработки в Codex*

## Продукт в одном абзаце
Подписочный сервис доставки продуктов по оптовым ценам из микро-дарксторов
(Алматы). Клиент платит членство 3 900 ₸/мес и заказывает продукты по цене
закупа с малой наценкой; доставка из даркстора в его квартале за 15–20 минут.
Витрина с ценами открыта всем (воронка подписки), заказы — только участникам
клуба. Оплата двухчастная: онлайн блокируется 80% расчётной суммы, остаток
клиент платит лично курьеру на ПОС-терминал по факту взвешивания.

## Состав системы и режимы работы
- **Бэкенд** — РЕАЛИЗОВАН и прогнан E2E: архив `online_store_koz_v5.zip`
  (Node.js/Express + PostgreSQL). Часть А ниже — его спецификация.
  - **Режим А (основной): развернуть готовый** по `RUN_LOCAL.md` из архива
    и работать только над фронтендом (Часть Б).
  - **Режим Б (запасной):** если ведётся собственная кодовая база бэкенда —
    довести её до спецификации Части А; готовые атомарные Codex-задачи
    с приёмкой — файл `CODEX_ПРОМПТЫ_КОЦ.md` (15 задач в порядке зависимостей).
- **Фронтенд** — разрабатывается с нуля по Части Б.
- **ЭТАП Ф-0 (гейт):** развернуть бэкенд, прогнать чек-лист RUN_LOCAL.md,
  прислать вывод заказчику. Без закрытого Ф-0 остальные работы не начинаются.

## ИНВАРИАНТЫ ПРОДУКТА (вставлять преамбулой в каждый Codex-промпт)
1. Онлайн-оплата ОДНА — предавторизация 80% расчётной суммы. Остаток — лично
   курьеру на ПОС по факту веса. Никаких онлайн-доплат. Захват (capture) не
   превышает холд: при недовесе capture = итог, доплата 0 (partial capture).
2. Скидки и промокоды применяются к товарной части (не ниже 0); доставка
   оплачивается всегда полностью.
3. Весовые товары заказываются в килограммах (дробно, шаг 0,1); штучные —
   только целыми.
4. Создание заказа атомарно резервирует остаток; отмена и невыкуп возвращают
   товар на остаток.
5. Витрина (каталог, цены, остатки) публична — без токена; оформление заказа —
   только с токеном и активной подпиской.
6. Менеджер точки (store_operator) видит и меняет данные ТОЛЬКО своей точки
   (скоуп по user.store_id). Стоп-лист точки влияет только на её витрину.

# ЧАСТЬ А. БЭКЕНД — спецификация реализованной системы (v5)

## А1. Стек и архитектура
Node.js (ES-modules) + Express; PostgreSQL 16 через `pg` (чистый SQL, без ORM);
слои routes → controller → service → repository; ошибки —
`new AppError(status, message, code)`; денежные операции — в транзакциях
(BEGIN/COMMIT/ROLLBACK на клиенте пула). JWT (access + refresh-сессии в БД),
bcryptjs. CORS открыт. Мультитенантность — row-level по `store_id`
(«один магазин + фильтр»). Миграции идемпотентны: `database/schema.sql` +
`migrations/001…003`.

## А2. Модель данных (ключевое)
- `stores` — даркстор: name, address, operating_hours, delivery_time_min/max, status.
- `store_coverage` — привязка домов к точке: store_id, address («д. 4»),
  entrance_count, active. UNIQUE(store_id, address).
- `users` — роли: customer | store_operator | admin_catalog | admin_operations |
  admin_customers; у staff — password_hash, у store_operator — store_id.
- `customers` — денормализованная карточка клиента точки: user_id, store_id,
  subscription_status/start/end/auto_renew (эти поля читает гейт заказа).
- `customer_addresses` — store_coverage_id + подъезд/этаж/квартира/код домофона.
- `products` — каталог сети: category, unit, `price_per_unit` (цена сети),
  `company_price` (закуп), `is_weighted`, is_active.
- `store_inventory` — остатки точки: quantity NUMERIC, stock_quantity INT,
  `selling_price` (nullable локальная цена-override), `is_visible` (стоп-лист),
  status available|low_stock|out_of_stock, last_delivery_date.
- `orders` — деньги заказа: subtotal (товары), `discount_total`, `delivery_fee`,
  estimated_weight/actual_weight, `online_payment_amount` (холд 80%),
  `online_capture_amount` (захвачено), `pos_terminal_topup` (доплата ПОС),
  final_total, `fulfillment_window` same_day|next_morning, delivery_status,
  payment_status pending|online_paid|fully_paid|cancelled, delivered_at.
- `order_items` — quantity NUMERIC(10,3) (кг для весовых), price_per_unit
  (снапшот цены на момент заказа), line_total, estimated_weight.
- `payments` — method online|pos_terminal|kaspi…, amount, status, provider_payload.
- `subscriptions` — amount (3900), billing_period monthly|yearly, status
  active|paused|cancelled|expired, expires_at, next_billing_date, auto_renew.
- `promo_codes` — code, discount_type fixed_amount|percentage, discount_value,
  min_order_value, max_uses, usage_per_customer, valid_from/until, is_active;
  `promo_code_usage` — факт применения. `first_order_discounts` — приветственные
  3 000 ₸.
- `delivery_settings` (по точке) — `min_order_value_for_free_delivery` (5000),
  `delivery_fee` (500), `ordering_open_hour` (11), `ordering_close_hour` (20).
- Служебные: `order_status_history`, `audit_logs`, `notification_queue`,
  `user_consents` (согласия ПДн при регистрации), `user_sessions` (refresh).

## А3. Бизнес-правила и формулы (сердце системы)
**Деньги заказа при создании:**
```
goods      = Σ(qty × unit_price)            # qty в кг для весовых
discounts  = first_order_discount + promo_discount   # к товарной части
final      = max(0, goods − discounts) + delivery_fee
delivery_fee = goods < threshold ? fee_точки : 0
hold(80%)  = round(final × 0.8)             # payment_method='online'
```
**Пересчёт по фактическому весу (менеджер, до передачи курьеру):**
```
goods_actual = subtotal × (actual_weight / estimated_weight)  # только товары!
final        = max(0, goods_actual − discount_total) + delivery_fee
capture      = min(hold, final)             # partial capture при недовесе
pos_topup    = max(0, final − capture)      # платится курьеру на ПОС
```
**Окно приёма заказов** (Asia/Almaty, параметры точки, дефолт 11–20):
внутри окна → fulfillment_window='same_day', доставка сегодня 15–20 мин;
после закрытия → 'next_morning', delivery_date завтра, слот 'morning_from_11:00';
ночью до открытия → 'next_morning' сегодня с открытия.
**Резерв:** при создании заказа на каждую позицию атомарный
`UPDATE store_inventory SET quantity=quantity−q … WHERE id=$1 AND quantity>=q`;
пусто → 409 product_reservation_conflict. Отмена/failed → возврат остатков
одним UPDATE…FROM order_items.
**Подписка:** POST активирует сразу (первый платёж подтверждает вебхук
провайдера, grace 3 дня; рекуррент — токеном у провайдера); повторная
активная → 409; отмена по умолчанию МЯГКАЯ (auto_renew=false, доступ до конца
периода), immediate=true — немедленная; пауза (админом) блокирует заказы.
**Промокод:** валидация до оплаты (активность, срок, min_order_value, лимиты
использований); скидка percentage — от товарной части; не суммируется
с приветственной скидкой.
**Гейт заказа:** нет токена → 401; нет активной подписки → 403 subscription_*.

## А4. Статусная машина заказа (delivery_status)
```
new ──► picked ──► in_delivery ──► delivered   (терминальный)
 │        │             │
 │        │             └─► failed («не открыл дверь»; возврат остатков)
 ├─► failed
 └─► cancelled   picked ─► cancelled            (возврат остатков; терминальные)
```
Переход в `delivered`: записывает платёж pos_terminal (=pos_topup, completed),
ставит payment_status='fully_paid' и delivered_at. Оплата на ПОС = закрытие сделки.

## А7. Приёмка бэкенда (= гейт Ф-0)
Чек-лист RUN_LOCAL.md: гостевая витрина → OTP-регистрация с согласиями →
подписка (дубль 409) → заказ (весовой 1,5 кг + штучный; доставка +500 ниже

→ отчёт точки (gmv = online_part + pos_part) → отмена нового заказа →
остаток вернулся.

# ЧАСТЬ Б. ФРОНТЕНД

**Стек:** React 18 + Vite + react-router (допустим Vue 3 — один фреймворк на
всё). Без UI-китов. Монорепо: `apps/client` (клиент, mobile-first PWA),

## Б2. Общий API-слой (`packages/api`)

1. `baseURL` из env (`VITE_API_URL`, дефолт http://localhost:3000/api).
2. JWT в `Authorization: Bearer`; хранение access-токена в памяти + localStorage;
   на 401 — попытка refresh (`POST /auth/refresh`, см. auth.routes), при провале —
   разлогин и редирект на вход.
3. Все суммы с бэка — строки NUMERIC: парсить Number(), форматировать
   `toLocaleString('ru-RU')` + « ₸». Веса — до 3 знаков, отображать «1,5 кг».
4. Ошибки API `{ message, code }` — показывать тостом; коды из блока
   subscription_* дополнительно открывают пейволл подписки (см. 3.8).

## Б3. Клиентское приложение `apps/client` (mobile-first PWA)

### Инварианты клиентского UX (нарушение = возврат задачи)
- Витрина и цены видны ГОСТЮ без входа. Вход требуется на оформлении.
- Оплата на сайте ОДНА — предавторизация 80% расчётной суммы. Вторая часть —
  лично курьеру на ПОС по факту веса. UI обязан это объяснять (блок «Оплата
  в две части» в корзине и оформлении).
- Промокод применяется к товарной части (не ниже 0), доставка платится всегда.
- Весовые позиции: количество в кг с шагом 0,5 в степпере (ввод вручную —
  шаг 0,1), подпись «итог по факту веса ±10%».

### Экраны

**3.1 Главная `/`** — герой из Figma Desktop-4: заголовок «Оптовые цены прямо

Приёмка: страница открывается без токена, обе CTA работают.

**3.2 Витрина `/shop`** — `GET /products/store/:storeId` БЕЗ токена.
storeId — из env (`VITE_STORE_ID`), на пилоте одна точка.
Категории (маппинг enum → русские названия), сетка карточек: фото-заглушка,

**3.3 Корзина `/cart`** — позиции со степперами и удалением; прогресс до

с delivery_settings точки»); поле промокода → `POST /promocodes/validate`

блок итогов: Товары / Промокод −X / Доставка / **Итого (предварительно)** /
рамка-блок «ОПЛАТА В ДВЕ ЧАСТИ»: «Сейчас на сайте — 80%: N ₸» + «Курьеру на
ПОС-терминал, по факту веса: ~M ₸» + подпись «итог станет окончательным после
взвешивания». Кнопка «Оформить».
Приёмка: цифры блока совпадают с ответом POST /orders с точностью до тийына.

**3.4 Оформление `/checkout`** — гейт: без токена → экран входа; далее адрес:
селект дома из зоны точки (на пилоте — статический список coverage; TODO-метка
на GET домов при появлении эндпойнта), подъезд/этаж/квартира/код домофона;
блок оплаты = копия «двух частей» из корзины; кнопка «Оплатить N ₸ (80%) картой».

delivery_address_id, items:[{product_id, quantity}], promo_code? }.
Ответ: order_number, breakdown, payment_options.online.preauth_amount.
Ошибка с кодом subscription_* → пейволл 3.8. Успех → экран 3.5.
Платёжный виджет провайдера — ЗАГЛУШКА (кнопка сразу «успех»): интеграция

Приёмка: заказ с весовым 1,5 кг создаётся; при корзине ниже порога в ответе

**3.5 Успех заказа `/order-success`** — номер заказа, «заблокировано N ₸ (80%)»,

**3.7 Личный кабинет `/profile`** — `GET /my-profile`; подписка: статус, дата

## Б4. Кабинет менеджера `apps/staff` → зона `/manager`

Вход: `POST /auth/staff/login` {email, password} → роль store_operator.
Всё скоупится точкой менеджера автоматически (бэкенд).

**4.1 Дашборд `/manager`** — `GET /my-store/analytics`: воронка дня (новые/
собраны/в пути/доставлены/невыкуп), GMV, взято на ПОС, средний чек; счётчики
остатков (стопы, out_of_stock, low_stock).

**4.2 Заказы `/manager/orders`** — `GET /my-store/orders`, фильтр по статусу,
автообновление 30 сек. Карточка заказа: позиции (вес/кол-во), адрес (дом,
подъезд, этаж, кв, домофон), суммы (итог / холд 80% / доплата ПОС).
Действия по статусной машине:
- new: **«Собрать»** → `PUT /my-store/orders/:id/pick` (чек-лист позиций в UI);
- picked: **«Фактический вес»** → ввод числа кг → `PUT .../actual-weight`
  {actual_weight}; показать пересчёт: итог, capture, доплата ПОС;
  затем **«В пути»** → `PUT .../status` {delivery_status:'in_delivery'};
- in_delivery: **«Доставлен · оплата ПОС получена»** → status delivered
  (кнопка активна только после чекбокса «оплата на ПОС принята»);
  **«Не открыл дверь»** → status failed (confirm: «товар вернётся на остаток»);
- new|picked: **«Отменить»** → status cancelled (confirm).
Приёмка: полный цикл new→delivered меняет payment_status на fully_paid;
отмена возвращает остаток (проверить на витрине).

**4.3 Остатки и стоп `/manager/stock`** — `GET /my-store/inventory`: таблица
(товар, эффективная цена, остаток, статус); тумблер «Стоп» →
`PUT /my-store/inventory/:productId` {is_visible}; правка локальной цены
(selling_price, пусто = цена сети) и корректировка остатка там же.
**Приёмка поставки:** кнопка у позиции → ввод веса/кол-ва →
`PUT /my-store/inventory/:productId/receive` {quantity}. Менеджер вводит
ТОЛЬКО количество — закупочных цен в его интерфейсе нет вообще.

## Б5. Admin-lite `apps/staff` → зона `/admin` (роли admin_*)

Минимум для пилота, таблицы без украшательств. Точные пути — admin/*/routes.

**5.1 Точки `/admin/stores`** — список (`GET /admin/catalog/stores`: подписчики,
дома, настройки доставки); создание (name, address + дефолтные настройки
создаются бэком); привязка домов: `POST /admin/catalog/coverage`
{store_id, address, entrance_count}; настройки доставки: порог/стоимость/окно
(`PUT /admin/catalog/delivery-settings/:storeId`).
**5.2 Товары `/admin/products`** — список/создание/правка (name, category,
unit, price_per_unit «цена сети», company_price «закуп», is_weighted);
привязка к точке с ценой (эндпойнт inventory в admin/catalog.routes);
деактивация.
**5.3 Промокоды `/admin/promos`** — список/создание (code, fixed_amount|
percentage, discount_value, valid_until, min_order_value, usage_per_customer)/
деактивация. `.../admin/catalog/promo-codes`.
**5.4 Клиенты `/admin/customers`** — список с поиском и фильтром точки;
карточка (адреса, последние заказы); подписка: продлить/пауза/отмена.
**5.5 Отчёты `/admin/reports`** — по точке
(`GET /admin/operations/stores/:id/report`), выручка по сети
(`.../analytics/revenue`), скорость доставки/невыкуп (`.../analytics/delivery`),
реестр платежей (`.../payments`). Просто таблицы + период.
